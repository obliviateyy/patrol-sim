# 项目需求

本项目为结课作品，目标是在浏览器中实现可操作的巡检机器人二维仿真。用户打开页面后，可以查看地图、发出移动指令，并看到机器人的位置、朝向和运行状态。

计划完成的版本为**基础版全部完成**。拟实现的功能范围为：Web 界面与二维地图、后端 API、手动控制、状态反馈、Git 版本管理、基础 CI 和 Docker 部署。标准版专项方向待选定后补充，当前骨架已预留模块入口，见[项目架构与接口](03_项目架构与接口.md)。

## 基础版（最低目标）

| 需求 | 验收方式 | 本骨架对应实现 |
| --- | --- | --- |
| Web 界面与二维地图 | 打开页面，能看到至少一张二维地图，并辨认机器人和地图边界。若地图设置了障碍物，页面能区分障碍物与可通行区域。 | `frontend/index.html`、`style.css`、`app.js`；20×15 网格，障碍物为深灰格，机器人为带朝向箭头的红点 |
| 后端 API | 按接口说明发出请求，能获取地图或机器人状态，并能通过接口发送手动控制指令。 | `GET /api/map`、`GET /api/robot`、`POST /api/robot/move` |
| 手动控制 | 在 Web 页面发出移动指令，机器人按指令移动。尝试越出地图边界时，机器人保持在地图内。 | 前进/左转/右转按钮；越界或撞障碍时位置不变 |
| 状态反馈 | 操作后能在页面看到机器人更新的位置、朝向和运行状态。页面显示与 API 返回的状态一致。 | 状态面板由 API 返回值渲染，每 2 秒轮询同步 |
| Git 版本管理 | 提交可访问的项目仓库地址，能查看源码和开发过程中的提交记录。 | 使用自己的仓库，按功能分次提交 |
| 基础 CI | 仓库能自动运行至少一项与项目相关的检查，例如测试或构建。能查看运行结果。 | `.github/workflows/ci.yml` 运行 10 项 pytest 用例 |
| Docker 部署 | 按文档执行 Docker 部署步骤，能打开页面并完成一次手动控制。 | `backend/Dockerfile` + `docker-compose.yml`，访问 8000 端口 |

## Git 协作与验收

1. **使用自己的项目仓库。** 从模板创建个人或小组仓库后，首次推送前用 `git remote -v` 确认 `origin` 指向自己的项目仓库。小组成员在同一个项目仓库协作，PR 也以该项目仓库的分支为合并目标。
2. **按任务保存进度。** 完成一项功能、修复或文档更新后，检查差异并单独提交。标题写清具体改动，建议使用 `feat`、`fix`、`docs` 等前缀。验收时可以从提交记录看出项目的开发过程，提交次数由实际工作决定。
3. **按项目规模选择分支流程。** 个人项目可以直接向默认分支提交。小组项目建议先同步默认分支，再创建 `feat/manual-control` 这类短期任务分支。完成检查后用 PR 合并，在 PR 里写明改动、实际执行的检查和结果。遇到冲突时与相关成员核对后再合并。
4. **提交前检查文件和结果。** 确认提交只包含本次任务相关的文件，排除密码、令牌、本地依赖目录和可重新生成的构建产物。交付时确认验收人员能查看仓库、提交历史和基础 CI 的实际运行结果。小组成员的工作内容可结合[小组分工](02_小组分工.md)核对。
